# E0891: Blocking Sleep Reached From a Suspend Function

## Explanation

`time.sleep` and `time.sleep_millis` are compatibility APIs that block the
current OS thread. A `suspend fn` must not reach either operation directly or
through synchronous helper functions because doing so would occupy the async
executor instead of yielding to its reactor.

The compiler checks the complete transitive call graph, including public
functions imported from project modules. The diagnostic reports only function
and API names in the call path; it never includes argument values or secrets.
Synchronous functions and legacy isolated native workers may continue to use
the blocking APIs.

## Error Example

```nomo
import std.time

fn pause() -> void {
    time.sleep_millis(100)
}

suspend fn main() -> void {
    pause()
}
```

This reports the path `main -> pause -> time.sleep_millis`.

## Correct Code

Until the RFC 0035 timer-runtime slice is implemented, keep blocking sleep out
of suspend call graphs:

```nomo
import std.time

fn blocking_main() -> void {
    time.sleep_millis(100)
}

fn main() -> void {
    blocking_main()
}
```

After the nonblocking timer API is implemented, suspend code will use
`task.sleep(duration)` and handle its `Result<void, TaskError>`.

## Fix

Use the nonblocking `task.sleep` API after its owner-local timer runtime lands,
or move the entire blocking operation behind the bounded blocking pool. Do not
wrap `time.sleep` in another helper: the compiler follows the transitive call
graph and still reports E0891.

## LSP Code Action

No automatic code action is provided because choosing between a timer and the
blocking pool changes cancellation, deadline, and ownership behavior.
